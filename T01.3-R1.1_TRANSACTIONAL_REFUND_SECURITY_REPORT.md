## 1. Executive Summary

During the T01.3-R1 independent security review of the Razorpay refund webhook processing pipeline, critical consistency and integrity vulnerabilities were flagged:
1. **Lack of Multi-Document ACID Transactions:** In webhook handlers (`refund.processed` and `refund.failed`), updating the refund status, updating the payment balance, canceling the booking, releasing holds, and updating the webhook event record were performed as disparate sequential database calls. If a failure or disconnect occurred mid-pipeline, the refund record landed in a terminal status while financial balances remained unsynchronized and pending amounts remained locked or uncollected.
2. **Silent Clamping of Financial Balances:** Payment balance settlement and release operations clamped negative balances to `0` using MongoDB `$max: [0, { $subtract: ['$pendingRefundPaise', amountPaise] }]`. This masked double-settlement bugs and balance drift, silently destroying financial invariants.
3. **Ambiguous Refund Matching:** When provider refund IDs or receipt references were absent, fallback matching defaulted to the payment's most recent pending refund, leading to accidental misattribution in concurrent multi-refund flows.
4. **Side Effect Leakage on Aborted Operations:** Audit logs and guest notifications were dispatched within the execution path before transaction commitment, causing phantom logs and notifications even if database operations subsequently failed.

Under task **T01.3-R1.1**, full transactional consistency, strict invariant balance validation, deterministic refund matching, and post-commit side-effect isolation have been implemented across the Poyokka payment platform. Real MongoDB replica set integration tests and 24 adversarial unit test scenarios verify that zero partial state is ever written, invariant violations strictly reject with `ConflictError`, and all quality gates pass 100%.

## 3. Remediation Architecture & Technical Implementation

### 3.1. ACID Multi-Document Transactions (`WebhookService`)

`WebhookService.handleRefundProcessed` and `WebhookService.handleRefundFailed` are now wrapped in `this.repo.withTransaction(async (session) => { ... })`.

Within a single atomic session:
1. **Validation & Locking:** Target refund and payment records are located using the transactional `ClientSession`.
2. **Refund Status Transition:** Atomic transition of the refund record from `INITIATED`/`PENDING` to `PROCESSED` or `FAILED`.
3. **Payment Balance Mutation:**
   - On `refund.processed`: calls `settleRefundBalance(paymentId, amountPaise, session)`.
   - On `refund.failed`: calls `releaseRefundBalance(paymentId, amountPaise, session)`.
4. **Booking & Inventory Restoration (Processed Only):**
   - For full refunds (`isFullRefund === true`), updates booking status to `CANCELLED`.
   - If the payment's associated hold is `CONSUMED`, calls `this.bookingsRepo.releaseHold(payment.holdId, undefined, session, true)` to restore room inventory units.
   - If the hold is not `CONSUMED` (e.g., expired or active), zero inventory is restored, preventing phantom room creation.
5. **Webhook Event Record Status:**
   - Webhook event record is created or updated to `PROCESSED` with `processedAt: new Date()` within the same session.

**Atomicity Guarantee:** If any error occurs (e.g. database disconnect, lock contention, balance conflict), the entire transaction aborts. The refund record, payment balance, booking status, inventory holds, and webhook event status all roll back atomically to their pre-transaction states.

### 3.2. Strict Reserved Balance Invariants & Removal of Silent Clamping

In `PaymentsRepository.settleRefundBalance` and `PaymentsRepository.releaseRefundBalance`:

1. **Elimination of Silent Clamping:**
   - Removed:
     ```ts
     // INSECURE PREVIOUS IMPLEMENTATION:
     pendingRefundPaise: { $max: [0, { $subtract: ['$pendingRefundPaise', amountPaise] }] }
     ```
   - Replaced with atomic conditional query filter:
     ```ts
     const query = {
       _id: toObjectId(paymentId),
       status: PaymentStatus.CAPTURED,
       pendingRefundPaise: { $gte: amountPaise },
     };
     ```
2. **Enforcement of Invariant:**
   `cumulativeRefundedPaise + amountPaise <= capturedAmountPaise` is strictly validated. In MongoDB, an aggregation-based pipeline update ensures:
   ```ts
   $cond: [
     { $and: [
       { $gte: ['$pendingRefundPaise', amountPaise] },
       { $lte: [{ $add: ['$cumulativeRefundedPaise', amountPaise] }, '$amountPaise'] }
     ]},
     // Updates:
     {
       pendingRefundPaise: { $subtract: ['$pendingRefundPaise', amountPaise] },
       cumulativeRefundedPaise: { $add: ['$cumulativeRefundedPaise', amountPaise] }
     },
     // Fallback: unchanged (causes update to match 0 documents)
     '$$ROOT'
   ]
   ```
3. **Explicit Error Rejection:**
   If the document cannot be updated due to balance invariant violation, the repository inspects the existing record and throws:
   - `new ConflictError('INSUFFICIENT_PENDING_REFUND_BALANCE')` when `pendingRefundPaise < amountPaise`.
   - `new ConflictError('EXCESS_CUMULATIVE_REFUND')` when `cumulativeRefundedPaise + amountPaise > capturedAmountPaise`.
   This guarantees balance errors are never silently swallowed or coerced to `0`.

### 3.3. Strict Webhook Payload Validation & Deterministic Refund Matching

1. **Payload Schema Validation:**
   In `WebhookService.processWebhook`:
   - Validates mandatory fields: `providerRefundId` (`rfnd_*`), `providerPaymentId` (`pay_*`), `amount` (positive integer), and `currency` (`INR`).
   - If any field is missing or invalid, the event is marked `FAILED` with an explicit reason (`MISSING_PROVIDER_REFUND_ID`, `MISSING_PROVIDER_PAYMENT_ID`, `MISSING_REFUND_AMOUNT`, `MISSING_CURRENCY`) and safely returns `{ received: true, event, eventId, status: 'FAILED' }` without touching any financial records.
2. **Elimination of Ambiguous Lookup:**
   In `WebhookService.findTargetRefund`:
   - Strict deterministic matching only:
     1. Search by `providerRefundId` (`refundRepo.findRefundByProviderRefundId(providerRefundId, session)`).
     2. Search by `refundReference` in notes/receipt (`refundRepo.findRefundByReference(refundReference, session)`).
   - Removed the dangerous fallback: `this.refundRepo.listRefundsByPaymentId(payment._id)`. Webhooks without deterministic matching strictly return `REFUND_NOT_FOUND`, preventing misattribution across concurrent refunds on the same payment.

### 3.4. Idempotency & Post-Commit Side Effect Isolation

1. **Idempotency Protection:**
   If a webhook for `refund.processed` or `refund.failed` is delivered repeatedly:
   - The handler checks if `targetRefund.status` is already `PROCESSED` or `FAILED`.
   - If already in that terminal state, it skips balance updates, inventory mutations, and booking cancellations, returning:
     `{ received: true, eventId, refundId: targetRefund._id.toString(), status: 'ALREADY_PROCESSED' }`.
2. **Post-Commit Isolation for Notifications & Audit Logs:**
   - Audit logs (`this.auditService.logSecurityEvent`) and notifications (`this.notificationService.publishEvent`) are deferred until after `withTransaction` successfully returns.
   - If the transaction aborts, zero audit logs and zero notifications are emitted.
3. **In-Memory Concurrency Serialization (`inMemoryTxLock`):**
   - For unit testing in in-memory mode, implemented an asynchronous mutex lock `inMemoryTxLock` to serialize in-memory transactions, accurately emulating MongoDB document-level write locks and preventing snapshot overwrite races during concurrent webhook tests.
