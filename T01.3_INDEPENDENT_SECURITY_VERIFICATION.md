## 3. Detailed Security Findings

### FINDING HIGH-01: Razorpay `refund.*` Webhook Events are Ignored
- **Severity**: HIGH
- **Location**: `server/src/modules/payments/webhook.service.ts:308-320`
- **Description**:
  In `webhook.service.ts`, the webhook processor explicitly matches only three event types:
  - `event === 'payment.captured'` (line 156)
  - `event === 'payment.failed'` (line 251)
  - `event === 'payment.authorized'` (line 287)
  All other incoming Razorpay webhook events fall through to line 308:
  ```typescript
  } else {
    // Other events ignored
    await this.repo.updateWebhookEventStatus(
      webhookEventRecord._id,
      PAYMENT_WEBHOOK_STATUSES.IGNORED,
    );
    return { received: true, event, eventId: providerEventId, status: 'IGNORED' };
  }
  ```
  Consequently, standard Razorpay refund events (`refund.processed`, `refund.failed`, `refund.created`) are discarded as `IGNORED`. If a refund was placed into `REFUND_PENDING` (or `status: PENDING`) due to upstream timeout or gateway async processing, an asynchronous webhook callback from Razorpay will never update the database record.
- **Impact**:
  Payments that enter `REFUND_PENDING` remain stuck in that state indefinitely unless manually intervened in the database.
- **Remediation**:
  Implement handlers in `webhook.service.ts` for `refund.processed` and `refund.failed` that update the corresponding `RefundModel` document and call `settleRefundBalance` or `releaseRefundBalance`.

---

### FINDING HIGH-02: Absence of Durable Background Refund Reconciliation Worker
- **Severity**: HIGH
- **Location**: `server/src/modules/payments/` & `server/src/loaders/server.ts`
- **Description**:
  While Poyokka possesses a background worker for booking hold expirations (`bookingHoldExpiryService`) and push notifications (`delivery.worker.ts`), there is **no background worker or cron job** that polls or reconciles pending refunds.
  If an upstream call times out (`PAYMENT_GATEWAY_TIMEOUT`) after Razorpay has committed the refund to the banking network, Poyokka sets the refund to `PENDING` and payment to `REFUND_PENDING`. There is no autonomous reconciliation task that queries `GET /v1/payments/{payment_id}/refunds` to synchronize with Razorpay.
- **Impact**:
  Admin staff must manually inspect stuck payments. If an admin unaware of the pending timeout initiates a second refund with a **different** idempotency key, and remaining balance exists, Razorpay could process a duplicate payout.
- **Remediation**:
  Create `refundReconciliationWorker` running on a 5-minute schedule to query Razorpay's API for any `RefundModel` in `status: PENDING` or `PROCESSING` older than 10 minutes.

### FINDING MEDIUM-01: In-Memory Balance Computation in `settleRefundBalance` and `releaseRefundBalance`
- **Severity**: MEDIUM
- **Location**: `server/src/modules/payments/payments.repository.ts:359-380` & `410-425`
- **Description**:
  In `reserveRefundBalance` (lines 303-322), Poyokka correctly uses an atomic MongoDB expression:
  ```typescript
  $expr: {
    $lte: [
      { $add: [{ $ifNull: ['$cumulativeRefundedPaise', 0] }, { $ifNull: ['$pendingRefundPaise', 0] }, amountPaise] },
      '$amountPaise',
    ],
  }
  ```
  However, in `settleRefundBalance` (lines 359-380), the update is computed in Node.js memory:
  ```typescript
  const p = await PaymentModel.findById(paymentId).session(session || null);
  if (!p) return null;
  const currentCumulative = (p.cumulativeRefundedPaise || 0) + amountPaise;
  const currentPending = Math.max(0, (p.pendingRefundPaise || 0) - amountPaise);
  // ...
  return PaymentModel.findByIdAndUpdate(paymentId, {
    $set: { cumulativeRefundedPaise: currentCumulative, pendingRefundPaise: currentPending, ... }
  });
  ```
- **Impact**:
  If two separate partial refund requests for the same payment are settled concurrently across cluster nodes without an encompassing MongoDB replica set transaction session, Thread B's `$set` could overwrite Thread A's updated `cumulativeRefundedPaise`, leading to state inconsistency.
- **Remediation**:
  Refactor `settleRefundBalance` to use atomic `$inc`:
  ```typescript
  $inc: {
    cumulativeRefundedPaise: amountPaise,
    pendingRefundPaise: -amountPaise,
  }
  ```

### FINDING LOW-01: Idempotent Replay Stale Status Trap
- **Severity**: LOW
- **Location**: `server/src/modules/payments/payments.service.ts:712-734`
- **Description**:
  When an admin retries a refund with the same `idempotencyKey` after a network timeout:
  ```typescript
  const existingRefund = await this.refundsRepo.findRefundByPaymentAndIdempotencyKey(payment._id, input.idempotencyKey);
  if (existingRefund) {
    return {
      refund: this.mapRefundToDto(existingRefund),
      payment: this.mapPaymentToDto(latestPayment || payment),
      ...
    };
  }
  ```
  If `existingRefund.status` is `PENDING`, the replay returns the stale `PENDING` state without checking Razorpay to verify whether the transaction has transitioned to `processed` or `failed`.
- **Impact**:
  Admin is forced to wait for manual database correction rather than receiving an updated live status upon retry.
- **Remediation**:
  If `existingRefund.status === 'PENDING'`, trigger an on-demand status check against Razorpay before returning the replay response.

## 4. Refund Balance Accounting & Math Invariant Analysis

### Verified Invariant
$$\text{cumulativeRefundedPaise} + \text{pendingRefundPaise} + \text{requestedRefundPaise} \le \text{amountPaise}$$

### Analysis:
1. **Pre-Check Filter** (`payments.service.ts:736-746`):
   ```typescript
   const remainingBalance = Math.max(0, payment.amountPaise - (currentCumulative + currentPending));
   const requestedAmountPaise = input.amountPaise !== undefined ? input.amountPaise : remainingBalance;
   if (requestedAmountPaise <= 0 || requestedAmountPaise > remainingBalance) {
     throw new BadRequestError(..., 'INVALID_REFUND_AMOUNT');
   }
   ```
   Ensures that client input must be strictly positive and cannot exceed the calculated available balance.
2. **Atomic Database Reservation** (`payments.repository.ts:303-322`):
   Before contacting Razorpay, `reserveRefundBalance` executes a single atomic `findOneAndUpdate` with an `$expr` condition. In MongoDB, document-level write locking ensures that concurrent operations serialize. If two requests attempt to reserve 1,000,000 paise on a 1,500,000 paise payment simultaneously, the second write fails the `$lte` check and returns `null`.
   This was empirically verified in Test 43 of `payment-lifecycle.test.ts`.
3. **Monetary Unit Consistency**:
   All balance fields (`amountPaise`, `cumulativeRefundedPaise`, `pendingRefundPaise`, `refundAmountPaise`) are stored as 64-bit integer paise. Floating-point arithmetic is completely avoided throughout the pipeline.
4. **Zero & Negative Protection**:
   Zod schema `refundPaymentSchema` (`packages/validation/src/index.ts:360-366`) enforces:
   ```typescript
   amountPaise: z.number().int().positive().max(PAYMENT_RULES.MAX_AMOUNT_PAISE).optional()
   ```
   Zero and negative numbers are rejected at the HTTP boundary before reaching the service.

## 5. Razorpay Integration & Upstream Failure Recovery

### Verified Provider Implementation (`razorpay.provider.ts`)
1. **Authentication & Secret Isolation**:
   - Provider utilizes HTTP Basic Auth: `'Basic ' + Buffer.from(`${this.keyId}:${this.keySecret}`).toString('base64')`.
   - `keySecret` is kept in server memory and never echoed in API responses or error details.
2. **Gateway Timeout**:
   - Upstream fetch calls specify `signal: AbortSignal.timeout(10000)`, guaranteeing that hung gateway requests terminate after 10,000 milliseconds.
3. **Fail-Closed Network Abort Handling** (`payments.service.ts:794-822`):
   - When a timeout occurs (`PAYMENT_GATEWAY_TIMEOUT`), the system **refuses to release the reserved balance**:
     ```typescript
     if (isTimeout) {
       await this.refundsRepo.updateRefund(refundRecord._id, { status: REFUND_STATUSES.PENDING, ... });
       await this.repo.updatePayment(payment._id, { status: PAYMENT_STATUSES.REFUND_PENDING });
       throw err;
     }
     ```
   - This prevents the catastrophic double-spend vulnerability where a timed-out refund actually succeeded at the gateway but was released locally, permitting a second refund of the same funds.
4. **Definitive Failure Handling** (`payments.service.ts:824-844`):
   - If Razorpay definitively rejects the refund with a synchronous 4xx error (e.g. `BAD_REQUEST_ERROR`), the reserved balance is safely released back via `releaseRefundBalance` and the refund record is marked `FAILED`.

## 6. Idempotency & Concurrency Mechanics

1. **Compound Unique Index**:
   `refund.model.ts:132-135` enforces:
   ```typescript
   refundSchema.index({ paymentId: 1, idempotencyKey: 1 }, { unique: true, sparse: true });
   ```
   This prevents multiple refunds with identical idempotency keys on the same payment at the database index engine level.
2. **Replay Flow**:
   Submitting the same idempotency key executes `findRefundByPaymentAndIdempotencyKey` and returns the existing refund DTO with code 200, bypassing gateway calls and balance deduction.
3. **Different Idempotency Keys**:
   Using different keys correctly treats each request as a new partial refund, but each remains constrained by the remaining balance check and atomic reservation lock.

## 7. Booking & Inventory Safety (Zero Phantom Inventory)

### Verified T01.2 RISK-02 Remediation
In `payments.service.ts:864-881`:
```typescript
if (isFullyRefunded) {
  const booking = await this.bookingsRepo.findBookingById(payment.bookingId);
  if (booking && booking.status !== BOOKING_STATUSES.CANCELLED && booking.status !== BOOKING_STATUSES.EXPIRED) {
    await this.bookingsRepo.updateBooking(booking._id, { status: BOOKING_STATUSES.CANCELLED });
    
    // Check if inventory was consumed and release if needed
    const hold = await this.bookingsRepo.findHoldById(payment.holdId);
    if (hold && hold.status === INVENTORY_HOLD_STATUSES.CONSUMED) {
      await this.bookingsRepo.releaseHold(payment.holdId);
    }
  }
}
```

### Safety Assessment:
1. **Partial Refunds**: When `isFullyRefunded` is false, booking cancellation is skipped entirely. Booking remains `CONFIRMED`.
2. **Late Payments (Expired Holds)**:
   In a late payment scenario, the inventory hold status is `EXPIRED` (units were already restored to room inventory by the expiry worker).
   When an admin refunds this late payment:
   `hold.status === INVENTORY_HOLD_STATUSES.CONSUMED` evaluates to **FALSE**.
   `releaseHold` is **NOT** invoked.
   Room inventory available units remain exactly at initial capacity, preventing phantom inventory generation. (Empirically verified in Test 48).
